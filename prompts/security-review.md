# Рев'ю на предмет безпеки й зловживання вхідними даними

## Роль

Security-орієнтований рев'юер: шукаєш не "чи працює код", а "що станеться,
якщо викликач передасть зловмисний або просто неперевірений вхід".

## Мета

Знайти місця, де відсутня валідація вхідних даних дозволяє зіпсувати бізнес-
результат (напр. від'ємні суми, знижку понад 100%, переповнення) або
розкрити/прийняти дані, яким не місце в цьому шарі коду.

## Контекст

- Ціль: `app/src/quote.ts` — увесь публічний API (`estimateTotalCents`,
  `splitInstallments`, `formatMoney`).
- Домен: розрахунок кошторисів; результат згодом іде клієнту.
- Немає мережевого I/O, немає читання файлів/env у цьому модулі — фокус на
  контракті функцій, а не на класичних OWASP-векторах (SQLi/XSS тут немає).

## Обмеження

- НЕ переписуй код і не пропонуй фікс — тільки знахідки (фікс — окремий
  запит/промпт).
- НЕ вигадуй вектори, яких не існує в цьому файлі (без "а що якщо тут була б
  БД" — оцінюй код, що є).
- Максимум 5 знахідок, відсортованих за впливом на бізнес-результат.

## Acceptance criteria

- [ ] Для кожної знахідки: файл:рядок, який вхід її викликає, який хибний
      результат це дає.
- [ ] Явно перевірено: діапазон `discountPercent` (0..100 по контракту типу,
      але чи є рантайм-перевірка?), знак `hours`/`rateCents`, узгодженість
      типу `parts` із рантайм-перевіркою.
- [ ] Якщо ризиків немає — так і написано, без вигаданих зауважень.
- [ ] Явно сказано, чи покриває це тест (`quote.test.ts`).

## Формат відповіді

Список знахідок:
`РІВЕНЬ РИЗИКУ | файл:рядок | вхід, що ламає | наслідок | покрито тестом? так/ні`

## Stop

Після списку знахідок зупинись. Не виправляй і не додавай валідацію коду —
навіть якщо це просто.

## Той самий промпт у XML-діалекті

```xml
<task>Рев'ю на предмет валідації вхідних даних і зловживання бізнес-логікою</task>
<role>Security-орієнтований рев'юер контракту функцій, не стилю</role>
<context>
  <target>app/src/quote.ts (публічний API)</target>
  <domain>Розрахунок кошторисів, результат іде клієнту</domain>
  <note>Немає мережевого I/O в цьому модулі — фокус на контракті функцій</note>
</context>
<constraints>
  <no>переписувати код або пропонувати фікс</no>
  <no>вигадувати вектори, яких немає в файлі</no>
  <max_findings>5</max_findings>
</constraints>
<acceptance>
  <item>файл:рядок + вхід + наслідок для кожної знахідки</item>
  <item>перевірено: діапазон discountPercent, знак hours/rateCents, рантайм-перевірка parts</item>
  <item>якщо ризиків немає — прямо сказано</item>
  <item>сказано, чи покрито тестом</item>
</acceptance>
<format>РІВЕНЬ | файл:рядок | вхід | наслідок | покрито_тестом</format>
<stop>Після списку знахідок. Без фіксів.</stop>
```

## Прогін (2026-09-14)

Знайдено 1 знахідку — спершу залишено без фіксу навмисно, щоб
продемонструвати, що review-промпт лише репортить (фікс — окрема задача, не
виконана в межах цього прогону):

`СЕРЕДНІЙ | app/src/quote.ts:20 (estimateTotalCents) | discountPercent: 150 або hours: -5 | функція мовчки повертає від'ємну або "надуту" суму замість помилки | покрито тестом? ні`

**Оновлення (2026-09-14, той самий день):** частину знахідки — `discountPercent`
поза межами `0..100` — полагоджено окремим запитом: `estimateTotalCents`
тепер кидає `Error`, регресійні тести додано (`quote.test.ts`, "кидає помилку
для discountPercent поза межами 0..100"). Валідація знаку `hours`/`rateCents`
із тієї ж знахідки **лишається невиправленою** — про це прямо сказано в
[`app/README.md`](../app/README.md) як відомий ризик, що чекає окремого фіксу.

> Урок: "review-промпт лише репортить" — це правило для одного прогону
> промпту, а не рішення "цей ризик ніколи не фіксимо". Знахідку review-типу
> варто або фіксити наступним запитом, або явно тримати в бекграунді — але
> не залишати документ і код неузгодженими.

> **Нотатка про діалект:** різниці в якості знахідки не помітив — обидва
> діалекти привели до однієї й тієї самої знахідки. XML тут трохи зручніший
> для формату відповіді (`<format>` як окремий тег легше зіставити з
> шаблоном рядка), markdown — швидше писати вручну.
