# Чек-ліст санітизації даних для роботи з AI

Багаторазовий чек-ліст команди: пройдіть його перед тим, як вставити будь-який
клієнтський матеріал (бриф, тікет, лист, лог, транскрипт дзвінка, вигрузку з
БД) у промпт, файл проєкту чи чат з AI-інструментом — публічним чи
корпоративним. Не є переказом одного конкретного брифу — застосовується до
будь-якого документа, який потрапляє на стіл команди.

Робочий приклад застосування — [`docs/sanitized-brief.md`](./sanitized-brief.md)
(санітизована версія `materials/client-brief.md`).

## 1. Що шукаємо (світлофор)

| Категорія | Приклади | Куди можна |
|---|---|---|
| 🔴 Секрети | API-ключі, токени (Slack `xoxb-…`, PAT, JWT), паролі, connection strings, SSH/cloud-креденшели, `.env`-файли, webhook-URL з вбудованим токеном | нікуди; лише out-of-band через env/secret manager |
| 🔴 PII клієнтів і третіх осіб | ПІБ, email, телефон, адреса, месенджери/хендли, номери документів, IP-адреси, дані співробітників клієнта | нікуди в спільну/публічну модель |
| 🔴 Продакшн-дані | вигрузки таблиць, логи з реальними користувачами, дампи БД, скріншоти CRM/адмінки | нікуди; замінити синтетикою того самого формату |
| 🟡 Внутрішня комерція | маржа, собівартість, ціноутворення, умови угоди, знижки, дедлайни щодо конкурентів | лише інструмент з no-train/enterprise-політикою (див. §5) |
| 🟡 Внутрішня логіка | назви внутрішніх систем і хостів, схеми БД, назви репозиторіїв/гілок, архітектурні деталі, internal-only URL | лише інструмент з no-train/enterprise-політикою (див. §5) |
| 🟢 Постановка задачі | опис проблеми, acceptance criteria, обсяги без даних, назви публічних SaaS-інтеграцій (CRM/Slack/Sheets як тип, не як конкретний тенант) | будь-яка модель |

**Правило за замовчуванням:** якщо категорія факту неочевидна — класифікуйте
за суворішим варіантом (🔴, а не 🟡), доки хтось із команди не підтвердить
пом'якшення. Два питання, які знімають більшість сумнівів:
1. Чи ідентифікує цей факт конкретну реальну людину або систему?
2. Чи буде шкода, якщо цей факт піде далі, ніж поточний чат?

Так на будь-яке з двох → 🔴 або 🟡, ніколи не 🟢.

## 2. Як класифікувати — процес

1. Пройдіть документ **зверху вниз один раз**, позначаючи кожен факт кольором
   світлофора — не намагайтесь одразу маскувати, спершу лише розмітьте.
2. Окремо перевірте секції, які зазвичай ховають 🔴 попри "внутрішній"
   заголовок секції (напр. "Доступи", "Конфігурація", "Для довідки") —
   заголовок не гарантує, що там немає секретів.
3. Лише після розмітки застосовуйте маскування (§3) — так простіше побачити,
   чи не замаскували забагато (задача стала незрозумілою) чи замало
   (лишився реальний факт під виглядом "начебто вже безпечного").

## 3. Як маскуємо

| Техніка | Коли застосовувати | Приклад "до → після" |
|---|---|---|
| **redaction** — прибрати повністю | факт не потрібен для задачі взагалі | `Telegram: @oksana_p_1987` → `<REMOVED>` |
| **masking** — лишити форму, прибрати значення | формат важливий для валідації/логіки, значення — ні | `+380 (67) 111-22-33` → `+380 (XX) XXX-XX-XX` |
| **synthetic** — замінити правдоподібним вигаданим | потрібен приклад того самого типу даних (ім'я, рядок вигрузки) | `Оксана Петренко` → `[CONTACT_1]`; рядок вигрузки → новий вигаданий рядок того самого формату (не похідна від реального!) |
| **out-of-band** — значення не потрапляє в текст узагалі | будь-який секрет/креденшел | `CRM API key` → `<SECRET_OUT_OF_BAND>` (значення — лише в env під час запуску) |

**Правило перевірки:** після маскування дайте документ колезі, який задачі не
знає. Якщо він(вона) все ще розуміє, що треба зробити — маскування вдале.
Якщо задача стала незрозумілою — замаскували зайве (типова помилка:
редагувати назви систем/інтеграцій, які потрібні для розуміння скоупу).

## 4. Що робити з креденшелами окремо

Секрети — єдина категорія, де немає "трохи можна" тіру. Правила без винятків:

- Жодне значення ключа/токена/пароля/connection string не потрапляє в
  промпт, у файл проєкту, у git — навіть частково, навіть з `fake`-схожим
  виглядом "про всяк випадок" (звичка копіювати "схоже на фейкове" — це той
  самий рефлекс, що одного разу скопіює справжнє).
- У документі лишається лише **назва** інтеграції й **назва env-змінної**,
  звідки агент візьме значення під час запуску (`CRM_API_KEY`,
  `SLACK_BOT_TOKEN` тощо) — цього достатньо, щоб задача була виконуваною.
- Значення передаються через env / secret manager на етапі запуску, ніколи
  через чат чи файл, який хтось (людина чи модель) читає як контекст.
- Least privilege: якщо агенту потрібен доступ до продакшн-ресурсу — видайте
  read-only/scoped токен під конкретну задачу, а не повний production-ключ.
- Якщо секрет випадково потрапив у чат, документ чи коміт — це інцидент:
  ротуйте/відкликайте його негайно; видалення повідомлення чи `git revert`
  саме по собі проблему не закриває (історія й кеші моделі можуть лишитись).

## 5. Інструмент під категорію

| Категорія | Інструмент / режим | Чому |
|---|---|---|
| 🟢 | будь-яка модель, звичайна підписка | немає що втрачати — це вже публічна постановка задачі |
| 🟡 | enterprise-підписка з no-train/zero-retention політикою (DPA), або локальна/on-premises модель | дані не йдуть на тренування і не зберігаються постачальником довше сесії; on-prem — коли навіть це недостатньо |
| 🔴 | жоден AI-інструмент не отримує ці дані як контекст; якщо агенту потрібна дія з секретом — лише out-of-band через env/secret manager під час виконання | будь-яке потрапляння в контекст моделі (навіть no-train enterprise) — це вже канал витоку, який не можна відкликати |

## 6. Перед тим, як вставити в модель

- [ ] Пройшовся пошуком по: `key`, `token`, `secret`, `password`, `postgres://`,
      `xoxb-`, `Bearer `, `@` (email/handle), `+380`/іншому формату телефону
- [ ] Немає жодного справжнього ПІБ / email / телефону / адреси
- [ ] Вигрузки й приклади даних — синтетичні, того самого формату, не похідні
      від реальних значень
- [ ] Секрети — лише через env/secret manager, не в промпті й не у файлі
- [ ] Внутрішня комерція (маржа, собівартість, умови) прибрана або позначена
      `<INTERNAL>`, якщо не потрібна для задачі
- [ ] Обраний інструмент відповідає **найвищій** категорії, що лишилась у
      документі (одна 🔴-згадка — і весь документ поводиться як 🔴)
- [ ] Колега, не знайомий із задачею, підтвердив: документ усе ще зрозумілий

## Який tier/інструмент обрати для 🟡-даних — і чому

Для 🟡-даних (внутрішня комерція, назви систем, архітектурні деталі) команда
обирає **enterprise-підписку з активним no-train/zero-retention режимом і
підписаним DPA**, а не безкоштовний чи персональний тариф публічної моделі:
у no-train режимі провайдер контрактно зобов'язаний не використовувати
запити для тренування моделей і не зберігати їх довше технічно необхідного
для відповіді, що закриває головний ризик 🟡-рівня — витік у майбутню видачу
моделі іншому користувачу чи в довгостроковий лог постачальника. Локальну /
on-premises модель тримаємо як опцію для окремих клієнтів із власною
compliance-вимогою "дані не залишають периметр" (рідше, ніж no-train-tier,
бо дорожче в підтримці й зазвичай слабша модель) — а не як дефолт для всіх
🟡-даних. 🔴-дані в жодному з цих режимів усе одно не з'являються як текст
контексту — no-train знімає ризик тренування, а не ризик самого факту
потрапляння секрету чи PII в чат.
